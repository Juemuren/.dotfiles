# 收集工具问题

## 判断问题是否需要收集

根据问题类型：

- 只有当问题来自工具链、权限或开发环境时才需要收集；项目代码本身的错误或测试产生的输出不需要收集。
- 只有当问题可复现或反复出现，并持续污染终端信息流时才需要收集；一次性或预期内的输出噪声不需要收集。

根据任务完全情况：

- 如果使用替代方案完成了任务，且新方案相比旧方案无明显缺点，那么不需要收集原方案的问题。
- 如果问题导致任务无法继续，那么需要收集问题。

## 判断任务是否可以继续

- 不要仅因为问题需要收集就停止主任务。遇到阻塞任务的环境问题时，先尝试安全、仍在任务范围内且不会明显降低结果质量的替代方案。
- 如果替代方案可行，就继续完成主任务，再按上述条件判断是否需要收集问题。

## 编写问题报告

文件位置：

- 将报告以 Markdown 文件格式保存到项目的临时目录下。如果项目中没有临时目录，那么创建 `<project-root>/tmp` 作为临时目录。
- 如果遇到了多个边界清晰的不同问题，那么需要将每个问题保存为一个文件。
- 文件名要能够反映出问题的概要，并使用 `kebab-case` 命名规则。

文件内容：

- 在 Front Matter 中写上标题和任务是否完成。
- 在正文中记录复现方式、问题分析和修复建议。
  - 复现方式部分：说明 Agent 如何复现该问题，并拷贝输出中的警告、错误等消息。
  - 问题分析部分：总结问题产生的原因，并简述问题的严重程度。
  - 修复建议部分：如果有多种修复方式，按推荐的顺序逐一列举；如果修复建议较为复杂，用修复流程、修复原理、修复适用情况作为子标题组织内容。
